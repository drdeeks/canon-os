# Canon OS Hackathon Standards

## Purpose

This is the release and documentation standard for Canon OS's OpenAI Build
Week submission. It applies to the derived hackathon blueprint, implementation,
demo video, repository, and Devpost entry. The master product blueprint remains
unchanged at `../../blueprint.md`.

## Official submission requirements

Submit by **July 21, 2026 at 5:00 PM PT** in **Work & Productivity**.

- Build a working project using Codex and GPT-5.6.
- Include a clear project description and a category.
- Provide a public YouTube demo under three minutes.
- Narrate what was built and how both Codex and GPT-5.6 were used; a music-only
  screencast is insufficient.
- Provide a repository URL. A public repository needs an appropriate license;
  a private repository must be shared with `testing@devpost.com` and
  `build-week-event@openai.com`.
- Include setup/run instructions and sample data when needed.
- Submit the `/feedback` Codex Session ID covering the majority of core work.
- If the project pre-dated the event, clearly distinguish the work completed
  during the submission period with dated commits and/or Codex session evidence.

Source: [OpenAI Build Week on Devpost](https://openai.devpost.com/).

## Product truth standard

Every public claim must be demonstrable in the supplied build and video.

| Capability | Acceptable claim | Required label when not live |
|---|---|---|
| Creative generation | Generated by the named configured backend | `Demo fixture` or `sample output` |
| Analytics | Imported metrics from a named source | `Sample analytics` |
| Social distribution | Previewed/scheduled platform content | `Publishing preview — not posted` |
| Backend registry | Selected backend is visible in the UI | `Unavailable` with a recovery path |
| Optimization | Recommendation derived from shown metrics | `Sample-data recommendation` |

Never present a mock, fixture, static image, or planned integration as a live
generation, social post, or autonomous learning outcome.

## Repository standard

The repository must contain:

1. A short product overview and the target user/problem.
2. Exact quick-start commands, prerequisites, configuration variables, and a
   no-secret demo path.
3. One sample image/brief or instructions for obtaining them.
4. Test commands and expected outcomes.
5. A feature-status table that distinguishes working, demo-backed, and deferred
   capabilities.
6. `docs/hackathon/CODEX_BUILD_LOG.md` with dated decisions, relevant commits,
   Codex contribution, GPT-5.6 contribution, and `/feedback` Session ID.
7. An open-source license if the repository is public.

No secrets, customer assets, private URLs, or model weights belong in version
control. API credentials are environment references only.

## Engineering and experience standard

- Preserve immutable campaign identity after creation; start a new campaign to
  change brand DNA.
- Show progress, error, retry, and provenance states in the dashboard.
- Make all primary controls keyboard reachable and give uploaded/generated
  images meaningful alt text.
- Verify the main flow at desktop and narrow viewport widths.
- Avoid default-path downloads of large models or dependencies during judging.
- Keep external-provider failure recoverable and preserve the user's inputs.
- Use Impeccable only after the core flow is working: run `init`, then
  `critique`, `audit`, and `polish` against the dashboard.

## Loop-enforcement standard

The derived blueprint is the source for its own generated checklist:

1. Validate `CANON_OS_HACKATHON_BLUEPRINT.md` before generation.
2. Generate checklist data in loop mode with validators enabled.
3. Initialize the chain once from that generated data.
4. The creator supplies evidence; a different reviewer verifies behavior.
5. The enforcer—not the creator—advances `active → pending_verify → verified → complete`.
6. A failed phase is repaired and re-verified; completed phases stay closed.
7. Finish with an independent Director review of product, docs, video, and
   Devpost draft together.

Do not hand-edit generated checklist files, state files, marker files, or
validators. Change the derived blueprint, validate it, then regenerate only
the derived artifacts that no longer match it.

## Video standard

Use this three-minute structure:

| Time | Content |
|---|---|
| 0:00–0:20 | Customer problem and Canon OS promise |
| 0:20–1:55 | Live image/brief to brand profile, script, storyboard, and creative draft |
| 1:55–2:25 | Platform variants, calendar, analytics provenance, backend selection |
| 2:25–2:50 | How Codex and GPT-5.6 accelerated the build |
| 2:50–3:00 | Outcome, repository, and truthful scope statement |

Record the actual product path. Do not cut together disconnected screens to
imply an automated flow that does not run end-to-end.

## Final release gate

Before submitting, an independent reviewer confirms all of the following:

- [ ] The documented setup creates a runnable judge experience.
- [ ] The demo's primary flow works with a sample input.
- [ ] Every sample/fixture/preview is labeled in product and documentation.
- [ ] The README, build log, video narration, and Devpost description agree.
- [ ] The video is public, under three minutes, and mentions Codex and GPT-5.6.
- [ ] The repository access and license state match the Devpost entry.
- [ ] The `/feedback` Session ID is recorded in the submission.
- [ ] The Devpost draft is complete before the deadline.
